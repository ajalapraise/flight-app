# Skyline — Flight Management Web App

Responsive flight booking app built for the internship technical assignment. Next.js 14 (App Router) + Supabase (PostgreSQL, Auth, Realtime) + Zustand + Tailwind. TypeScript everywhere, no `any`.

> **Status:** Tasks 1–4 complete. Task 5 (PWA bonus) intentionally skipped — see [What I didn't do](#what-i-didnt-do).

## Stack

| Concern | Choice |
|---|---|
| Framework | Next.js 14 (App Router, Server Components, Server Actions disabled by default) |
| Database | Supabase Postgres (RLS on every table, RPCs for all writes) |
| Auth | Supabase Auth (email/password) |
| Realtime | Supabase Realtime channel on the `seats` table |
| State | Zustand 4 with `persist` + `partialize` |
| Styling | Tailwind CSS |
| Language | TypeScript strict — no `any` anywhere in `src/` |

## Local setup

### 1. Create a Supabase project

1. Go to [supabase.com](https://supabase.com), create a new project, wait for it to provision.
2. **Project Settings → API**: copy the URL and the `anon` public key.
3. **Project Settings → API**: copy the `service_role` key — needed _only_ for the optional test-user seed script.

### 2. Run the migrations

In the Supabase dashboard, **SQL Editor → New query**. Paste and run each file in this order:

```
supabase/migrations/0001_init.sql       # tables, indexes, generate_pnr()
supabase/migrations/0002_rls.sql        # row-level security policies
supabase/migrations/0003_rpcs.sql       # reserve_seat, cancel_booking, reschedule_booking
supabase/migrations/0004_triggers.sql   # 2-hour cancellation guard
supabase/migrations/0005_seed.sql       # 8 flights / 4 routes / full seat maps
```

(If you have the Supabase CLI linked: `supabase db push` runs everything in order.)

### 3. Enable Realtime on `seats`

**Database → Replication → `supabase_realtime` publication → ✓ public.seats**. Without this, the seat map will still work but it won't update live when someone else books a seat.

### 4. Environment

```bash
cp .env.example .env
# fill in NEXT_PUBLIC_SUPABASE_URL and NEXT_PUBLIC_SUPABASE_ANON_KEY
```

### 5. Install + run

```bash
npm install     # or pnpm install / yarn
npm run dev     # http://localhost:3000
```

### 6. (Optional) Seed a test user

If you set `SUPABASE_SERVICE_ROLE_KEY` in `.env`:

```bash
npx tsx scripts/seed-test-user.ts
```

This creates the credentials below. **Or** sign up via the UI — Supabase Auth's "Confirm email" setting is on by default; turn it off under **Authentication → Providers → Email** if you want the signup flow to log you in immediately.

## Schema and concurrency design

### Tables (all in `public`)

`flights, seats, bookings, passengers, reschedules` — see `0001_init.sql` for the exact columns. Notable choices:

- **`bookings.pnr_code` is unique** and generated by `generate_pnr()` (6 chars from a 32-char alphabet, excluding confusable I/1/O/0). Collision-retry up to 10 times in the RPC.
- **`bookings_active_seat_idx`** is a partial unique index on `seat_id` where `status <> 'cancelled'`. This guarantees at the DB level that no seat can be in two non-cancelled bookings at once. If our application logic ever had a bug, Postgres would refuse the insert.
- Indexes are tuned for the actual access patterns: search by `(origin, destination, departs_at)`, list bookings by `(user_id, booked_at desc)`, find available seats with a partial index.

### Row Level Security

| Table | Anonymous | Authenticated user |
|---|---|---|
| `flights` | ✓ read | ✓ read |
| `seats` | ✓ read | ✓ read |
| `bookings` | — | ✓ read **own** rows only |
| `passengers` | — | ✓ read passengers belonging to own bookings |
| `reschedules` | — | ✓ read reschedules belonging to own bookings |

No `INSERT/UPDATE/DELETE` policies are written on `bookings`, `passengers`, `seats`. That's deliberate: every mutation goes through a `SECURITY DEFINER` RPC that does the right business logic atomically. The RPC checks `auth.uid()` against the row owner — so RLS-equivalent ownership is enforced even when bypassing RLS via security-definer.

### The seat-locking RPC — `reserve_seat`

The brief calls out double-booking race conditions explicitly. The RPC does it in one transaction:

1. `SELECT ... FOR UPDATE` on the seat row — concurrent reservers block here.
2. Re-check `is_available` (it may have flipped while we were waiting on the lock).
3. Flip `seats.is_available = false`.
4. Insert the booking row (the partial unique index `bookings_active_seat_idx` is a second safety net).
5. Insert the passenger row.

If two clients call this concurrently for the same seat, exactly one wins. The other gets `seat_unavailable` and the SeatMap drops its optimistic selection on the next Realtime tick.

### Atomic cancel — `cancel_booking`

Single transaction: `UPDATE bookings.status = 'cancelled' WHERE id = $1` plus `UPDATE seats.is_available = true WHERE id = booking.seat_id`. Ownership check (`booking.user_id = auth.uid()`) up front.

### The 2-hour cancellation rule — enforced at DB level

The brief is explicit: "Cancellations within 2 hours of departure must be blocked (**enforced at DB level**)". Migration `0004_triggers.sql` installs a `BEFORE UPDATE OF status` trigger on `bookings` that raises `cancel_window_closed` if anyone — including a future code path that bypasses our RPC — tries to flip status to `cancelled` within 2 hours of `flights.departs_at`. Belt and braces.

### Reschedule — `reschedule_booking`

Same atomicity pattern: lock the new seat, validate same-route, free the old seat, claim the new one, update `bookings.flight_id` and `total_price`, insert a `reschedules` row with `fee_charged = max(0, new_total - old_total)`. PNR and `booking.id` are preserved so the user's reference doesn't change after a reschedule.

## Zustand store structure

Two stores, both in `src/store/`.

### `useFlightStore` (`flight-store.ts`)

Holds the in-progress booking. Fields:

- `searchQuery` — `{ origin, destination, date, passengers }`
- `selectedFlightId`
- `selectedSeatId` (this is the **optimistic** selection — set immediately on click, before any DB write)
- `currentStep` — `'search' | 'select-flight' | 'select-seat' | 'passenger' | 'review' | 'done'`
- `passengerForm` — `{ full_name, passport_no, nationality, dob }`

Actions: `setSearchQuery`, `setSelectedFlight`, `setSelectedSeat`, `setStep`, `updatePassengerForm`, `reset`.

**Persistence (`partialize`):** searchQuery / selectedFlightId / selectedSeatId / currentStep / passengerForm survive a reload, **but `passenger_no` is stripped on write** — passport numbers are sensitive PII and we keep them in memory only. The user has to re-enter the passport number on resume.

### `useUserStore` (`user-store.ts`)

Auth session + cached bookings.

- `userId`, `email` — kept in memory only.
- `sessionToken` — persisted. Hint for the UI; Supabase's own cookie handles real session refresh via the middleware.
- `cachedBookings` — persisted snapshot of `/bookings` so that page reads from cache on offline visits. Populated by `<CacheBookingsForOffline />` after each successful server fetch.

`reset()` wipes both stores. Called on logout and on booking cancellation success.

### Optimistic seat selection — why it's safe

Clicking a seat sets `selectedSeatId` immediately (Task 04 requirement). The actual seat reservation only happens when the user submits the booking form. Between click and submit, the seat is still `is_available = true` in the DB, so it can theoretically be taken by another user. If that happens, the SeatMap's Realtime handler patches the local copy to "occupied" and clears our selection if it was the same seat. If we somehow race past that — for instance both users click "Confirm" at the same millisecond — the `FOR UPDATE` lock in `reserve_seat` serializes us, and the loser gets `seat_unavailable` as a human-readable error.

## Responsive design

- Layout breakpoints: `sm` (640), `md` (768), `lg` (1024). Booking page collapses to a single column below `lg`.
- Seat map is wrapped in `overflow-x-auto` and has a `min-w-[320px]` inner container so it never overflows the viewport. Seat cells are `min-h-[2rem]` so they remain comfortable touch targets.
- Header collapses the email address below `sm` to keep the nav from wrapping.
- All forms use system date/number inputs so mobile keyboards Just Work.

## Deployment

Standard Vercel flow:

1. `vercel link` or import the repo in the Vercel dashboard.
2. Add the same two env vars (`NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`) under **Project → Settings → Environment Variables**. Don't add the service-role key — it's only used by the local seed script.
3. In Supabase: **Authentication → URL Configuration → Site URL** set to your Vercel preview URL so the email-confirmation redirect works.
4. Push to `main` → Vercel builds and deploys.
